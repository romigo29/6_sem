## 1. Что сделано

В качестве тестируемого приложения взят серверный модуль курсового проекта
(`CoursePSKP/server/src/services/*.js`). Тесты написаны для трёх сервисов,

| Сервис | Ответственность | Файл тестов |
|---|---|---|
| `bookingService` | запись на тренировку, отмена, списание занятия с абонемента | `tests/bookingService.test.js` |
| `subscriptionService` | покупка абонемента, заморозка, разморозка | `tests/subscriptionService.test.js` |
| `visitService` | генерация персонального QR, check-in по QR, декремент занятий | `tests/visitService.test.js` |

Все зависимости сервисов (Prisma-клиент, пакет `qrcode`) изолированы
через **тестовые заглушки (stubs)** и **mock-объекты** в терминологии
Jest. Курсовой код **не изменялся** — тесты работают поверх него в
режиме London-school (все внешние обращения замоканы).

### Статистика

```
Test Suites: 3 passed, 3 total
Tests:       15 passed, 15 total
Time:        ~1.6 s
```

По 5 тестов на каждый сервис: 1 happy-path + 4 ключевые ветки (ошибки/граничные случаи).


*Ranges* здесь — это V8-блоки функций, они играют роль приблизительного
branch coverage: каждый `if/else/catch`/ранний `return` порождает
отдельный диапазон, и мы считаем его покрытым при `count > 0`.

По `subscriptionService` покрытие ниже, потому что из 14 методов
сервиса юнит-тестами покрыты только `purchase` и `freeze` — этого
достаточно для демонстрации изоляции, но остальная половина файла
(планы, типы, отчёты админа) в расчёт покрытия тем не менее входит.

### Запуск

```bash
# просто тесты
npm test

# тесты + отчёт о покрытии
npm run test:coverage
```

> Почему свой `run-coverage.js` вместо штатного `jest --coverage`?
> Стандартный Istanbul-instrumentation в Jest, как и c8/nyc, ломается
> на путях с не-ASCII символами (в нашем случае — папки
> «6 семестр» и «ТПО»): матчеры глобов возвращают пустой список.
> Поэтому используется встроенное V8-покрытие
> (`NODE_V8_COVERAGE=coverage/tmp`), которое с путями проблем не имеет,
> а агрегацию результатов делает `coverage-report.js`.

## 2. Примеры использования тестовых двойников

### Stub: подменяем Prisma-клиент
```js
const mockPrisma = createPrismaMock();
jest.mock('../../../CoursePSKP/server/src/config/prisma',
         () => mockPrisma);

mockPrisma.training.findUnique.mockResolvedValue({
  id: 10, trainerId: 2, maxSlots: 5,
  startAt: new Date('2026-05-01T10:00:00Z'),
  _count: { bookings: 3 },
});
```
Это **заглушка (stub)**: методу `findUnique` задан фиксированный
возврат — он имитирует работу БД, но сам в БД не ходит.

### Mock: проверяем факт вызова и аргументы
```js
expect(mockPrisma.booking.create).toHaveBeenCalledTimes(1);
expect(mockPrisma.userSubscription.update).toHaveBeenCalledWith({
  where: { id: 77 },
  data: { remainingSessions: { decrement: 1 } },
});
```
Это уже **мок (mock)**: мы не только задали поведение,
но и проверяем, что SUT правильно вызвал зависимость.

### Virtual mock: подменяем внешний npm-пакет
```js
jest.mock('qrcode',
  () => ({ toDataURL: jest.fn(async () => 'data:image/png;base64,STUB_QR') }),
  { virtual: true });
```
Пакет `qrcode` в Lab09 не установлен — его и не нужно ставить,
потому что virtual mock перехватывает `require('qrcode')` ещё
до резолвинга модулей.

## Ответы на вопросы

### 1. Кто и когда проводит юнит-тестирование?

Юнит-тестирование проводят **разработчики** (автор кода или его
коллеги по команде) **во время** написания продуктивного кода —
либо **до него** (TDD, test-first), либо **сразу после** реализации
каждого модуля. Дополнительно юнит-тесты автоматически
прогоняются:
- на локальной машине перед коммитом (git hooks, IDE);
- на сервере CI при каждом push/pull request;
- на ночных билдах как часть регрессии.

Тестировщики (QA) юнит-тестами обычно не занимаются — это зона
ответственности инженеров, которые пишут код. QA отвечает за
интеграционное, системное и приёмочное тестирование.

### 2. Преимущества и недостатки юнит-тестирования

**Преимущества:**
- очень быстрый фидбэк (миллисекунды на тест);
- ранняя ловля дефектов — чем раньше найдена ошибка, тем дешевле
  её исправить;
- живая документация: по тестам видно, *как* автор ожидал
  использовать модуль;
- безопасный рефакторинг — тесты страхуют изменения;
- улучшают дизайн: код, который легко тестировать, обычно имеет
  чёткие границы и низкое зацепление (low coupling);
- позволяют реализовывать TDD и CI.

**Недостатки:**
- занимают время: на юнит-тесты уходит 20–40 % времени разработки;
- требуют поддержки — при рефакторинге падают не только плохие
  тесты, но и хрупкие хорошие;
- не ловят ошибки интеграции (правильные модули могут быть
  неправильно склеены);
- высокое покрытие ≠ высокое качество: можно покрыть 100 % строк,
  не проверив важные инварианты;
- чрезмерное использование моков приводит к тестам, которые
  «тестируют моки, а не код».

### 3. Структура юнит-теста (AAA)

Каждый тест состоит из трёх чётко выделенных блоков:

1. **Arrange (подготовка)** — создаём объекты, настраиваем
   заглушки, готовим входные данные;
2. **Act (действие)** — вызываем ровно один метод SUT (system
   under test) с подготовленными входами;
3. **Assert (проверка)** — сравниваем фактический результат с
   ожидаемым, проверяем вызовы зависимостей, состояние объектов.

Пример из `bookingService.test.js`:
```js
test('бронирование без абонемента', async () => {
  // Arrange
  mockPrisma.training.findUnique.mockResolvedValue({
    id: 10, trainerId: 2, maxSlots: 5,
    startAt: new Date('2030-01-01'), _count: { bookings: 0 }
  });
  mockPrisma.userSubscription.findFirst.mockResolvedValue(null);
  mockPrisma.booking.create.mockResolvedValue({ id: 99 });

  // Act
  const result = await BookingService.book(1, 10);

  // Assert
  expect(result.id).toBe(99);
  expect(mockPrisma.userSubscription.update).not.toHaveBeenCalled();
});
```

Преимущество AAA — тест читается сверху вниз как маленькая
спецификация: «Дано… Когда… Тогда…».

### 4. Зачем изолировать тестируемые юниты?

Изоляция нужна, чтобы тест проверял поведение **ровно одного**
модуля и ничего больше. Без изоляции:

- **тест становится медленным** — поход в настоящую БД/сеть превращает
  юнит-тест в интеграционный и тормозит его на порядки;
- **тест становится нестабильным** — падает из-за чужих ошибок,
  сбоев сети, неотчищенных данных предыдущих тестов;
- **тест трудно локализовать** — если падает, непонятно, виноват
  ли наш модуль или его зависимость;
- **тест трудно воспроизвести** — реальные зависимости могут
  возвращать разные результаты на разных окружениях (время,
  состояние кэша, случайность);
- **нельзя проверить редкие ветки** — например, обработку ошибок
  БД: специально уронить настоящую БД ради теста — так себе идея.

Изолируя юнит тестовыми двойниками, мы получаем детерминированный,
быстрый и точный тест: падает — значит, баг именно в проверяемом
модуле.

### 5. Тестовые двойники

Классификация по Джерарду Месарошу (xUnit Test Patterns):

| Двойник | Что делает | Когда применять |
|---|---|---|
| **Dummy** | объект-пустышка, передаётся только для заполнения параметров, не используется | метод требует параметр, но в данном тесте этот параметр реально не трогает |
| **Stub** | возвращает заранее заданные ответы на вызовы, состояние не проверяем | нужно подать SUT определённые входные данные от зависимости |
| **Spy** | stub + запоминает, как его вызывали, можно запросить историю | нужно подтвердить факт вызова *после* `Act` |
| **Mock** | spy + заранее заданные ожидания; провал ожидания = провал теста | проверяем протокол взаимодействия с зависимостью (кого, когда, с какими аргументами вызвали) |
| **Fake** | рабочая, но упрощённая реализация (in-memory БД, временная FS) | зависимость слишком сложна, чтобы её мокать целиком, но настоящая — слишком тяжела (внешние БД, оплата) |

В работе:
- **stub** — `mockResolvedValue(...)` для Prisma-запросов, чтобы
  подать сервису нужные «данные из БД»;
- **mock** — `jest.fn()` + `toHaveBeenCalledWith(...)` для проверки,
  что `booking.create` вызывается с корректным payload;
- **virtual mock** — для пакета `qrcode`, которого нет в Lab09,
  но он требуется в `visitService`.

Dummy и Fake в лабе не использовались, т.к. все зависимости либо
возвращают данные (stub), либо проверяются на факт вызова (mock).

### 6. Виды покрытия. Как рассчитать покрытие?

Основные виды:

| Вид | Что считает | Формула |
|---|---|---|
| **Statement / Line coverage** | покрыта ли каждая исполняемая строка/инструкция | `выполненные_строки / всего_строк` |
| **Branch coverage** | покрыты ли обе ветки каждого условного перехода | `пройденные_ветки / всего_веток` |
| **Condition coverage** | покрыты ли оба исхода (true/false) каждого булева подвыражения | `покрытые_условия / всего_условий` |
| **Function / Method coverage** | вызвана ли каждая функция хотя бы раз | `вызванные_функции / всего_функций` |
| **Path coverage** | пройден ли каждый уникальный путь через CFG модуля | `покрытые_пути / всего_путей` |
| **MC/DC** | модифицированное условие/решение: каждое подусловие независимо влияет на результат (требуется в авиастандарте DO-178C) | — |
| **Loop coverage** | цикл пройден 0, 1 и N раз | — |

Покрытие **рассчитывается** инструментом инструментации кода
(Istanbul/nyc/c8 в JS, coverage.py в Python, JaCoCo в Java). Он
добавляет в каждую интересующую точку счётчик `hit++`, запускает
тесты и после прогона считает долю счётчиков со значением > 0.

В данной работе покрытие посчитано нашим собственным
`coverage-report.js` поверх V8-coverage (NODE_V8_COVERAGE). Формулы:

```
Line coverage  = покрытые_строки (есть непробельный покрытый символ) / всего_значимых_строк
Range coverage = range-диапазонов с count > 0 / всего_range-диапазонов
```

Итог по всему тестируемому коду: **36.4 %** строк, **60.0 %**
V8-блоков (аналог branch coverage).
